- [x] Existing reusable infra identified:
  - `HR_TM_FormDocNoMaster` = spec's `HR_FormDocMaster`, already live.
  - `HR_TM_TravelConfig` + `HR_TM_TravelConfigApprovers` = spec's `HR_ApprovalConfig` + `HR_ApprovalConfigApprover`, already live, same `ApprovalMode` CHECK constraint (`default_chain`/`any_one`/`selected_employee_override`), same nullable company/branch scoping.
  - `HR_TM_StatusMaster` (Id, Status) - existing ID-based status lookup, only 3 rows today (Pending/Approved/Rejected, resolved by keyword in `TravelSetupRepository.GetApprovalStatusIdsAsync`). Reused for the new engine (see decisions) instead of the spec's proposed varchar+CHECK columns.
- **Gap found, not just a naming mismatch**: the spec's `HR_ApprovalInstance`/`HR_ApprovalStep` (one row per required approver, arbitrary N) does not exist. What's live instead, `HR_TM_TripRequestApproval`, is a flat one-row-per-transaction table with exactly 3 fixed bit columns (`ClientApproval`/`FinanceApproval`/`HrApproval` = RM/Finance/HR). `TravelApprovalWorkflow.ResolveOverallStatusId` maps `selected_employee_override`'s arbitrary-length approver list onto those 3 slots by keyword-matching each approver's free-text `ApprovalType` tag against "hr"/"fin"/"report". **Two approvers both tagged "Finance Manager" cannot both be tracked** - only one `FinanceApproverEmpId`/`FinanceApproval` slot exists. This is the real reason to build the spec's per-approver step table, not gold-plating.
- Corrections to the spec's guessed schema:
  - `HR_TM_Trip` -> actually `HR_TM_TripRequest`.
  - `HR_TM_AdvancePayment` -> actually `HR_TM_TravelAdvancePaymentLine`, and it is **not** its own approval flow - it's a payment line hanging off an already-approved `HR_TM_TripRequestApproval` row (`TripRequestApprovalId` FK). The spec's `FormDocId=5` "Approve Advance Payment" as an independent `CreateInstance` target doesn't match reality.
  - `BranchMasterId` FK target resolved: `Unit.UnitMasterId`, not `HR_UnitMaster`/`HR_BranchMaster`.
- Decisions (user-confirmed 2026-09-28):
  1. **Engine scope**: full generic rebuild. Real `HR_ApprovalInstance`/`HR_ApprovalStep` (arbitrary N approvers per step, no 3-slot cap). Rename the TM config tables to be cross-module rather than leaving them Travel-only.
  2. **Rollout phasing**: PHASED. This module wires up the generic engine + renamed cross-module config tables, and connects **only Recruitment** (`approverequisition`/`hrapproverequisition`, `FormDocId` 1 and 2). `HR_TM_TripRequestApproval` and Travel Management's existing flat 3-slot tracking stay completely untouched and working as today - migrating Travel Management onto the new engine is an explicit future follow-up module, not part of this one.
  3. **Status modeling**: reuse the existing status master table (renamed generically, see Phase 2) rather than the spec's varchar+CHECK columns - keeps one status vocabulary instead of two, and Travel Management's `StatusName`-driven UI needs no translation layer once it eventually migrates. New rows needed for step-level `Skipped` and instance-level `Cancelled` (data only).

**Bug caught and fixed while wiring Recruitment**: `ResolveConfigSql`'s branch-match condition (`ac.BranchMasterId = @branchMasterId`) is never TRUE when both sides are NULL (SQL's three-valued logic) - and `HR_RecruitmentRequisition` has no `BranchMasterId` column at all, so Recruitment always calls `CreateInstance` with a null branch. Without the fix, a deliberately branch-agnostic (NULL) config row would silently fail its exact-match test and fall through to the global fallback arm - wrong result for exactly the module this table exists for. Fixed with `ISNULL(x, -1) = ISNULL(y, -1)` pairing on both sides.

**Cut over (2026-09-28, user decision)**: `UpdateApprovalRecruitmentRequisition`, `UpdateHRStatusRequisition`, `GetAllRecruitmentRequisitions` now route through the engine; `GetHRApprovalRequisitionList` deliberately does not (see below).

- **Design gap found while wiring this**: Recruitment has *two* independent approval tracks over the same `HR_RecruitmentRequisition` row ("Raise Requisition", "HR Approve Requisition" - spec §3.1), but the additive `ApprovalInstanceId` column (spec §3.6) only has room for one FK. Fixed by adding `IApprovalRepository.GetInstanceIdAsync(formDocId, transactionRecordId)`, which resolves either track independently via `HR_ApprovalInstance`'s own `UQ_HR_ApprovalInstance_Transaction` key. `ApprovalInstanceId` is kept only as a "most recently touched instance" convenience pointer, not the source of truth.
- **Cross-FormDoc chaining decision**: nothing in the spec says when the "HR Approve Requisition" instance gets created. Went with: when the raise-approval `Action` call closes `Approved`, `UpdateApprovalRecruitmentRequisition` immediately calls `CreateInstance` for "HR Approve Requisition" over the same row. This matches this codebase's own pre-existing intent - `GetHRApprovalRequisitionList`'s doc comment already said `[Status = Approved]` before any of this work started. Not spec-confirmed, flagged here in case wrong.
- **`GetHRApprovalRequisitionList` filtering (2026-09-28, user confirmed)**: initially left unfiltered on purpose, since its doc comment documented a prior deliberate "show all" decision. User explicitly asked to apply the same `GetPending`-based filtering here too, so this now shows only what's Pending on the caller at the "HR Approve Requisition" stage (FormDocId 2) - same mechanism as `GetAllRecruitmentRequisitions(applyApproverFilter: true)`, just against the other FormDoc.
- **"Reopen" transitions bypass the engine entirely**: `ApprovalStatus`/`HRStatus` values other than "Approved"/"Rejected" (case-insensitive) skip `Action` and fall through to the old column-update path unchanged - the engine's Pending→terminal state machine has no concept of reopening a closed instance, and inventing one wasn't asked for.
- **New real enforcement, not just a data-source swap**: both actions previously had zero server-side authorization - any authenticated caller could set any status on any requisition Id. `Action`'s pending-step lookup is now the actual boundary.

## Phase 8 - Travel Management migration (2026-09-28, user-requested follow-up)

Scoped via a research pass before any code: "migrate Travel Management" turned out to be three
differently-sized jobs, not one. Decisions:
1. **In scope this pass**: Trip Request approval + Advance Payment approval (share `HR_TM_TripRequestApproval`, differentiated by `FormDocId`/`FormName` - straightforward, same shape as Recruitment).
2. **Explicitly out of scope**: Travel Expense approval. It does NOT use `HR_TM_TripRequestApproval` at all - its steps are rebuilt dynamically on every read (`ApproveTravelExpenseRepository.BuildApprovalStepsAsync`) from live config, with its own duplicated any-one/unanimous logic and its own auth check, backed by `HR_TM_TripExpenseSubmit.SubmitStatus` + `HR_TM_TripExpenseSubmitApprovalLine` (a separate, `MERGE`-upserted table with defensive "does this exist yet" fallback code suggesting it's newer/less settled). Migrating this needs real design work (how dynamically-rebuilt steps map onto persisted `HR_ApprovalStep` rows), not a mechanical swap - a separate future module.
3. **Company/Branch-wide role visibility** (`TravelRoleScopeOptions`/`TripApprovalScopeResolver` - Travel Admins see the whole company, Finance/Accounts see their whole branch, regardless of personal approver assignment): the new engine's `GetPending` has no equivalent (it only ever answers "do I personally have a pending step"). **Not built as new engine capability this pass** - solved implicitly instead, see the dual-write decision below. Long-term direction (user-stated): don't revive the old appsettings-role-list mechanism as a bolt-on - the real fix is generalizing `HR_ApprovalConfig`/`HR_ApprovalConfigApprover` to accept *roles* as approvers/viewers directly, not just individual employees, once employee-level migration is solid. That's a real future piece of work, not started.

### Architecture: dual-write, not a union/cutover

Live module, real in-flight data in `HR_TM_TripRequestApproval` - a union-based list rewrite would
need a new cross-table Id scheme (real collision risk: two independent IDENTITY columns) and would
break the existing Company/Branch-wide visibility query, which only knows how to read that one
table. Instead:

- **Submission side** (`TripRequestRepository.AddTripRequest`/`AddTripRequestRange`): the existing
  `HR_TM_TripRequestApproval` row(s) are still written exactly as before (unchanged) - `BuildApprovalSeedAsync` still gates hard on missing config, matching existing behavior (unlike Recruitment,
  where a missing config is non-fatal - different modules, matched each one's own existing
  semantics rather than copying Recruitment's choice). *After* that transaction commits, a **separate**
  call creates the real `HR_ApprovalInstance`/`HR_ApprovalStep` rows via `CreateInstance` (one per
  FormDoc: Trip Request Approval, and Advance Payment Approval if applicable). This second call is
  non-fatal on failure (logged only) - by the time it runs, config is already known-good, so a
  failure here means something unrelated went wrong after the real trip request already saved
  successfully.
- **Action side** (`TripApprovalRepository.ApproveTrip` - also covers Advance Payment, which just
  delegates to this same method): before touching the legacy flat-column update, resolves the
  instance via `GetInstanceIdAsync(formDocId, tripRequestId)` and calls `Action`. Rows created
  before this migration have no matching instance and skip straight to the unchanged legacy logic.
  Rows created after it get real enforcement first (`NotAuthorizedApproverException`/
  `InstanceAlreadyClosedException` now mapped to 403/409 in `TripApprovalService.ApproveTrip`,
  matching the Recruitment cutover's HTTP contract) - only on success does the existing flat-column
  mirror update still run, unchanged, so **list/detail/Company-Branch-wide visibility keep working
  exactly as today for both old and new rows**, since they're still reading the same table they
  always read. This is *why* the role-visibility gap didn't need solving as a new engine capability
  this pass - the mirror table already serves it.
- **Real, load-bearing gotcha found while wiring this**: `ApprovalRepository.CreateInstanceAsync`/
  `ActionAsync` each manage their own transaction (`BeginTransactionAsync`/`CommitAsync` on the
  scoped `IDapperContext`). `DapperContext.BeginTransactionAsync` unconditionally opens a new
  transaction and `CommitAsync` unconditionally closes the connection - calling either from *inside*
  `TripRequestRepository`'s or `TripApprovalRepository`'s own already-open transaction (same scoped
  instance per request) would silently clobber the outer transaction and prematurely close the
  connection out from under it. Both engine calls are deliberately placed as their own separate,
  sequential transactions (after the trip's own commit; before the trip's own approve-transaction
  begins) - not a stylistic choice, a correctness requirement.

### Revision (2026-10-06): list visibility switched to strict `GetPending`, matching every other module

**Found while auditing Trip Request's full chain at the user's request** ("let us go slow and start
with this"): `TripApprovalService.ListAllTripApprovals` never used the generic engine's `GetPending`
at all - it used `TripApprovalScopeResolver` (a role-based company/branch-wide visibility model:
Travel Admin sees the whole company, Finance/Accounts their branch, deliberately preserved during
the original Phase 8 migration) plus an inline, hand-rolled `HR_ApprovalConfigApprover` `EXISTS`
check in `TripApprovalRepository.ListTripApprovalsForListAsync` for the non-admin case. That inline
check derives eligibility from **static config/role fields**, never from the actual
`HR_ApprovalStep` instance state - it could show a row as "yours" even when the engine's current
stage wasn't actually waiting on you yet (no `CurrentStageOrder` awareness at all).

**User's explicit decision**: replace this with strict `GetPending`-based filtering, identical to
Recruitment/Income Tax/FNF/every other module - no exceptions for any role, full stop.
Role/department/designation-based broader visibility (the thing `TripApprovalScopeResolver` was
reaching for) is an **explicit, deliberately deferred later scope**, not solved now.

- [x] `TripApprovalService.ListAllTripApprovals`: now fetches company-scoped rows only (basic
  tenant boundary, unrelated to "who may decide"), then filters to the caller's own
  `GetPending(formDocId, employeeId)` result set via `TransactionRecordId` (matched against
  `ListTripApproveDto.TripRequestId`, **not** `.Id` - `TransactionRecordId` was set to the trip
  request's own ID at `CreateInstance` time, not the `HR_TM_TripRequestApproval` row's PK, an easy
  mismatch to get wrong). A caller with no employee record sees nothing, same as every prior
  module's unresolvable-identity fallback.
- [x] `TripApprovalScopeResolver`/`TripApprovalListScope`/role-based `ApproverViewerEmpId` SQL in
  `ListTripApprovalsForListAsync` are left in place, now simply unreachable (nothing sets
  `ApproverViewerEmpId` or a non-Company `Scope` anymore) - not deleted, since the user's own framing
  ("roles, departments and designation... is a later scope") suggests this plumbing may be revisited
  when that broader-visibility work actually happens, rather than rebuilt from scratch.
- [x] **Scope note**: this pass only covers Trip Request Approval's list screen
  (`GetAllTripApprovalRequests`). Advance Payment Approval has its own separate controller/list
  endpoint and was **not** touched this pass - explicit next step, not forgotten.

## Phase 11 - Broader module rollout, module 5: Attendance Adjustment (2026-09-29)

**Attendance Adjustment** - done, including a new engine capability (see below).

**Correction to the earlier scoping note above**: reading `AttendanceAdjustmentRepository.ApplyDecision`'s
raw SQL (not just the service layer) showed the "two independent parties, each with their own
required column" framing was wrong. The real legacy rule is **first-decision-wins**: whichever of
{the employee's actual reporting manager} or {any HR/Admin} decides first - Approve *or* Reject -
sets the final outcome immediately (`GetPendingApprovals` excludes a row from the queue the instant
*either* column reaches a terminal state, and the HR-path SQL writes the shared `ApprovalStatus`
column too, not just its own `HRApprovalStatus`). The two status columns are for audit attribution
(which capacity made the call), not two independently-required gates.

None of the 3 existing modes can express that: `default_chain`/`any_one` always put the Reporting
Manager stage strictly *before* any other stage (HR's step isn't even actionable until RM's stage
resolves), and `any_one`'s reject rule is deliberately unanimous-within-the-stage (so one of several
equal approvers rejecting doesn't block the others) - the opposite of "one reject ends it".

**New engine capability, added for this module**: a fourth `ApprovalStageGroupMode`/`ApprovalModes`
value, `FirstDecisionWins` (`SolutionOne_Core/ApprovalModels/ApprovalWorkflow.cs`). At the config
level it puts Reporting Manager (if resolvable) and the whole configured approver pool together in
ONE stage (`StageOrder 0`); at the step-evaluation level, `ApprovalStepEvaluator.IsStageApproved`
treats it like `AnyOne` (any single Approved closes it), but `IsStageRejected` treats it like
`Unanimous` (any single Rejected closes it too) - the "first decision, either way, wins" property
neither existing mode has alone. Doesn't touch the other 3 modes' behavior or any of the 6
already-migrated flows.

- [x] `HR_AttendenceAdjustment` confirmed legacy-shared (deployment script, pre-existing seeded data) - untouched, no schema change.
- [x] `ApprovalRepository.GetReportingManagerIdAsync` fixed to `NULLIF(ReportingPersonID, 0)` - `ReportingPersonID` is `NOT NULL` and `0` is this codebase's own established "no reporting person set" convention (per `AttendanceAdjustmentRepository`'s own comment); without this fix, an employee with no manager would have resolved to a bogus `ApproverEmployeeId` of `0` instead of "no Reporting Manager step". Applies to every mode that calls this helper, not just the new one, though Attendance Adjustment is the first module to actually exercise a `0` in practice (every other module either doesn't hit it or guards it away upstream, e.g. Comp-Off's `InsertApplication`).

Naively passing the engine-filtered subset straight through would have meant "the engine refused every row" silently turned into "decide every row" whenever that subset was empty. ## Phase 11 - Broader module rollout, module 6: Leave Approval (2026-09-29)

**Leave Approval** - done, but deliberately **not** wired the way every other module is.

Per the deferred scoping above, this module keeps `HR_LeaveAppAuthLeavel` as the real
workflow/authorization engine and only dual-writes `HR_ApprovalInstance`/`HR_ApprovalStep` as a
**non-authoritative mirror**, for cross-module visibility (`GetPending`/`GetTeamRequests`/timeline)
- it never blocks a leave decision. This is the one module in the whole rollout where the engine is
not the enforcement boundary. Reasons, unchanged from the original scoping:

- `HR_LeaveAppAuthLeavel` supports arbitrary-length org-chain escalation (via the legacy

  employee's `LeaveApproverUserMasterID` is NULL today, so it always falls back to a single Level-1
  approver = the applicant's `ReportingPersonID`, which the engine's `default_chain`
  (`IsReportingMgrRequired=true` only) matches exactly.
- The signed `ReportingPersonId` convention (positive = `EmployeeMasterID`, negative =
  `-UserMasterID` for an HR-Admin approver with no employee record) has no schema equivalent in
  `HR_ApprovalStep.ApproverEmployeeId` (a bare, FK-constrained `bigint`). Unreachable today for the
  same all-NULL reason above.
- `LeaveApprovalRepository.ApplyDecisions` is a **batch across potentially several different leave
  applications, inside one shared EF transaction**, with each iteration's escalate-vs-settle branch
  decided by DB state re-read inside that same transaction - a loop-shaped hazard with no clean
  before/after seam to insert a gating `Action()` call into, unlike Comp-Off/Attendance Adjustment's
  batches (both turned out to open no transaction of their own at all).

**Submission side** (`LeaveApplicationService.InsertApplication`): `CreateInstance` after
`_repository.InsertApplication(...)` returns (that call's own EF transaction has already committed -
same "fully separate, sequential step" discipline as every prior module, no nesting hazard). Config:
`default_chain`, `IsReportingMgrRequired=true` only.

**Decision side** (`LeaveApprovalService.ApplyDecisions`): the real decision-making is completely
untouched - `_repository.ApplyDecisions` runs exactly as it always has, and its result is what the
caller sees. *After* that call returns (transaction already committed), a new
`MirrorDecisionsToApprovalEngineAsync` helper runs:
- Resolves the **distinct `LeaveApplicationId`s** touched by this batch from the already-loaded
  `queue` (which maps `LeaveAppAuthId -> LeaveApplicationId`).
- Re-reads each one's **current** `Status`/`ReportingPersonId` via a new
  `ILeaveApprovalRepository.GetOutcomesAsync` method (a fresh, lightweight query - not derived from
  `ApplyDecisions`' own aggregate `Approved`/`Rejected`/`Finalised`/`Escalated` counts, which don't
  say *which* application landed where). This is the only reliable way to tell "genuinely decided" 
  apart from "escalated to a further level" (unreachable today, but if it ever happens the engine's
  single-step mirror would just diverge safely, staying Pending) or "skipped inside the transaction
  as stale".
- For each application whose status is now `Approved`/`Rejected`, calls `Action()` using **that
  application's own `ReportingPersonId`** (frozen at submission time on `HR_LeaveApplication`, the
  same column/moment the engine's own Reporting-Manager step was created from) - not the acting
  session's identity, same reasoning as Comp-Off/Attendance-Adjustment-manager-side: an HR-Admin
  override shouldn't change who the engine thinks the authoritative approver is.
- **Every failure here is logged and swallowed, never surfaced or blocking** - `ApplyDecisions`'
  own `ResponseModel`/`LeaveApprovalResultModel` is unaffected either way. This is the load-bearing
  difference from every other module's gate.

## Phase 11 - Broader module rollout, module 7: FNF (2026-09-30)

**FNF (Full & Final Settlement) Approval** - done. Scoped via a dedicated research pass first (per
the user's own explicit request to understand the problems before implementing), which corrected
the original "separate, later conversation" framing in both directions:

- **Overcautious on transaction risk**: `FnfSettlementRepository` shares the exact same scoped
  `IDapperContext` as `ApprovalRepository`, but every one of its methods opens and commits its OWN
  independent transaction - there is no single transaction wrapping Approve's cascading side
  effects (push to payroll, settle loan schedule). This is actually the simplest transaction shape
  of the whole rollout - placing the engine gate as its own step before `ApproveCaseHeaderAsync`
  is safe, same discipline as every prior module.
- **Undercounted on authorization**: there was no "no approver-config concept", there was **no
  decision-level authorization at all** - `FnfCaseService.ApproveAsync`/`RejectAsync` checked only
  `WorkflowStatus`/checklist completeness, nothing case-specific, not even a blanket `IsAdmin()`
  check like Loan/Assets/Comp-Off had before their own migrations. This migration is genuinely
  adding real enforcement where none existed, not translating an existing rule.
- **Side effects entangle two other modules, neither in conflict**: Approve pushes into
  `HR_EmployeeWiseSalaryHead`/`HR_SalaryAdditionalHead` (plain payroll config tables, never
  approval-gated) and marks `HR_LoanEMISchedule.IsPaid` (an accounting/schedule table, distinct
  from `HR_LoanRequests`/`HR_LoanApproval` which Loan Request Approval already gates) - no
  interaction with any already-migrated gate.
- Single case, single decision, no batching - simplest shape of the whole rollout.

**A real, FNF-specific design problem found while wiring this, not present in any prior module**:
`RejectAsync` returns a rejected case to Draft for the SAME `caseId`, and the preparer is expected to
edit and resubmit it - a normal, common, expected part of this workflow (unlike every other
module's reject-is-terminal shape). Since `HR_ApprovalInstance` is uniquely keyed on
`(FormDocId, TransactionRecordId)` with no "reopen" concept (same gap already accepted for
Recruitment's Reopen transitions), a resubmission's `CreateInstance` call always fails on the
duplicate key (caught, logged, non-fatal) - and a subsequent decision would then resolve to the
STALE, already-closed instance from the first cycle. Handled by having the gate treat "instance
already closed" (HTTP 409, from `InstanceAlreadyClosedException`) as "fall through to the legacy
`WorkflowStatus` check" rather than a hard refusal, while still hard-blocking on "not authorized"
(HTTP 403) - the legacy `WorkflowStatus` check plus `ApproveCaseHeaderAsync`/`RejectCaseAsync`'s own
`rows == 0` optimistic-concurrency guard already catch a genuine double-decision race on the same
live pending case, so this doesn't reopen a real hole. **Known, disclosed limitation**: a case that
gets rejected even once permanently loses the new engine-level enforcement on all its future
decisions (every resubmission collides with the same stale instance) - strictly better than the
pre-migration baseline (zero enforcement for every case) but not as strong as first-time-clean

## Phase 13 - Trip Request/Approval consolidated onto `IRequestMetadata`; "Travel Config" messaging corrected (2026-10-06)

**Part 1 - duplicate claims-reading eliminated.** Found while auditing the Trip Request create flow
at the user's request: `TravelUserContext.FromHttpContext` (`TripRequestService`, `TripApprovalService`,
`AdvancePaymentApprovalService` each had their own copy of this call) re-read JWT claims directly off
`IHttpContextAccessor` - a second, parallel implementation of exactly what `IRequestMetadata` already
centralizes for every other service in this codebase. The only real reason it existed separately:
`IRequestMetadata`'s existing properties (`CompanyId`/`BranchId`/`UserId`/`EmployeeMasterId`) all
**throw** `MissingClaimException` when a claim is absent, and Travel Management's whole pattern is
built around "the claim might legitimately be absent" being a normal branch to check
(`viewer.EmployeeMasterId <= 0` for an Admin login with no employee record), not an error worth
throwing for.

**Fix, not a workaround**: extended `IRequestMetadata` itself (user's explicit go-ahead: "if you want
to implement more things in the requestMeta please feel free") rather than inventing a second
mechanism to route around the throwing one:
- `TryGetCompanyId`/`TryGetBranchId`/`TryGetUserId`/`TryGetEmployeeMasterId(out long value)` - tolerant
  companions to the existing throwing properties, same claim names, returning `false`/`0` instead of
  throwing.
- `RoleId` (tolerant, defaults to `0` - same "not wired up yet" caveat `TravelUserContext`'s own doc
  comment already carried) and `RoleNames` (every `ClaimTypes.Role` claim, `UserRole` folded in at the
  front if not already present - multi-role support `UserRole` alone never gave).
- `RequestMetadata.cs` internally refactored onto two shared private helpers
  (`GetRequiredLongClaim`/`TryGetLongClaim`) so the throwing and tolerant paths share one piece of
  claim-reading logic instead of two near-duplicates within the same file.

`TravelUserContext` itself is kept (its shape is depended on by `TripRequestScopeResolver`/
`TripApprovalScopeResolver`/`TravelApprovalAccessResolver`/`TravelRoleScopePolicy` - not worth a
wider signature rewrite across all of those for this) but its `FromHttpContext` factory is replaced
with `FromRequestMetadata(IRequestMetadata meta)`, built entirely from the new tolerant members - the
class no longer touches `IHttpContextAccessor`/`ClaimTypes` at all.

- [x] `TripRequestService`, `TripApprovalService`, `AdvancePaymentApprovalService`: `IHttpContextAccessor`
  dropped from the constructor entirely, replaced with `IRequestMetadata`; every ad-hoc inline
  `_httpContextAccessor.HttpContext?.User.Claims.FirstOrDefault(c => c.Type == "UserId")` block
  (there were 6 of these across the 3 files, each a near-identical copy) replaced with
  `_requestMetadata.TryGetUserId(out var uid)`.
- [x] **Drive-by correctness fix** in `AdvancePaymentApprovalService.ResolveTravelUserContextAsync`'s
  branch-fallback path: it rebuilt a new `TravelUserContext` when filling in a missing branch, but the
  object initializer never copied `RoleNames` across (silently reset to empty) - fixed while already
  touching this exact method; not something this pass went looking for.
- [x] Full build + full test suite (402/402) passing

**Explicitly not done, flagged as a separate, larger cleanup**: several other Travel Management
services (`TripExpenseSubmitService`, `TravelPolicyService`, `TravelPaymentService`,
`TravelConfigService`, `TravelSettlementService`) still read `IHttpContextAccessor` claims directly
with their own inline patterns, same root shape as what was just fixed here. Out of scope for this
pass (it was focused on the Trip Request/Approval chain specifically); worth revisiting as its own
pass if the same "why is there a separate implementation" question comes up for those screens too.

**Part 2 - "Travel Config" error-message text corrected to the real screen.** The actual admin screen

**Deliberately NOT renamed**: the `TravelConfigController`/`TravelConfigService`/

## Phase 14 - Trip Approval `Approve` endpoint: UserMasterId/EmployeeMasterId conflated, and a
## generic-approver column-resolution gap (2026-10-07)

**Bug report**: `POST /api/TripApproval/Approve` with `{"approvalType":"approver", ...}` threw
`System.ArgumentException: Invalid approval type` from
`TripApprovalRepository.ResolveApprovalColumn`, 500ing the whole request.

**Root cause, two separate things found together while auditing `TripApprovalController.cs` +
`ApprovalRepository.cs` per the user's explicit "we store EmployeeMasterID, let's not confuse
ourselves with UserMasterId" instruction:**

1. **Identity conflation.** `TripApprovalService.ApproveTrip` resolved both `callerUserId`
   (`TryGetUserId`) and `empId` (`TryGetEmployeeMasterId`), but only ever passed a single `uid` int
   into `ITripApprovalRepository.ApproveTrip(..., int uid, ...)` - at one point `callerUserId`, after a
   prior edit `empId`. That one parameter was overloaded for two different, incompatible meanings
   inside the repository: `ActionAsync`'s `EmployeeId` (must be EmployeeMasterID - the engine's
   `HR_ApprovalStep.ApproverEmployeeId` is always an EmployeeMasterID) and `LastModifiedBy` (an audit
   column that, by this table's own `CreatedBy = entity.EntryUserMasterId` convention set at insert
   time in `TripRequestRepository.InsertTripApprovalRowAsync`, is a UserMasterID). Whichever one was
   wired up, the other was silently wrong. The same conflation existed on the Advance Payment path:
   `AdvancePaymentApprovalService.ApproveAsync` passed `(int)callerUserId` (UserMasterID) straight
   through to the same repository method's `ActionAsync` call - meaning advance payment approvals
   routed through the Approval Engine were authorizing against the wrong id the whole time this was
   wired up, and would 403 (`NotAuthorizedApproverException`) for any user whose UserMasterID doesn't
   numerically equal their EmployeeMasterID.

   **Fix**: `ITripApprovalRepository.ApproveTrip` and `IAdvancePaymentApprovalRepository.ApproveAsync`
   now take both explicitly - `long employeeId` (engine gate + legacy-column resolution) and `int uid`
   (LastModifiedBy audit value only, unchanged meaning). Both service callers now resolve and pass
   both ids by name instead of coercing one into the other's slot.

2. **Generic-pool approval type.** `ResolveApprovalColumn(type, state)` only understood the three
   `default_chain` keywords (`"hr"`/`"fin"`/`"report"|"manager"|"rpt"`) baked in at the fixed-role era.
   `any_one`/`selected_employee_override` configs can have config-approver rows with no such role at
   all (`TravelSetupRepository.AssignUnmappedSelectedApprovers` slots them into
   Reporting/Finance/HrManagerEmpId purely positionally) - the FE has no meaningful keyword to send for
   those, hence `"approver"`, which matched nothing and threw.

   **Fix**: `ResolveApprovalColumn` now takes the acting `employeeId` too, and after the keyword checks
   miss, falls back to matching `employeeId` against `state.HrManagerEmpId` /
   `state.FinanceApproverEmpId` / `state.ReportingManagerEmpId` to find which legacy column this
   approver actually occupies - using the same EmployeeMasterID identity the engine itself already
   authorized against, not a client-supplied string.

Verified: full build (0 errors) + full test suite (402/402) after.

**Follow-up same day**: live testing against a 5-approver `selected_employee_override` config
(`1, 2, 7, 8, 9`, all `StageGroupMode = Unanimous`) surfaced the next layer of the same structural
gap - the legacy mirror table only has 3 approver slots at all
(`ReportingManagerEmpId`/`FinanceApproverEmpId`/`HrManagerEmpId`); `AssignUnmappedSelectedApprovers`
silently maps only the first 3 generic approvers and drops the rest. So even with the FK-fallback
above, a 4th/5th approver (here, employees `8` and `9`) matches no column at all.

Also caught in the same investigation: because `ActionAsync` commits in its own transaction *before*
`ApproveTrip` opens the transaction that writes the legacy mirror, a failure in the legacy-write half
(exactly what the original "Invalid approval type" bug caused) left the engine's decision committed
while the HTTP response reported a 500 - misleading a retry into a (correct, but confusing) 403
`NotAuthorizedApproverException`, since that approver's step was no longer pending. Not a bug in
itself (the two transactions are deliberately separate - see the method's existing comment on why),
but worth knowing: a failed `/Approve` response doesn't always mean nothing happened.

**Decision (user, 2026-10-07)**: when no legacy column matches, skip the legacy mirror write for that
approver entirely rather than throwing - `ActionAsync` already recorded their decision on the
authoritative engine instance/step; the legacy columns remain a best-effort mirror for the first 3
approvers only. `ResolveApprovalColumn` now returns `string?` (`null` = nothing to mirror) instead of
throwing `ArgumentException`, and `ApproveTrip` skips both the column-update and the
`TravelApprovalWorkflow.ResolveOverallStatusId` recompute when it gets `null`. Build (0 errors) + full
test suite (402/402) verified again after.

## Phase 16 - Overall trip Status prematurely flipped to "Approved" (2026-10-07)

Continuing the same live test: once 3 of 5 `selected_employee_override` approvers decided, the trip's
overall `HR_TM_TripRequestApproval.Status` flipped to "Approved" and blocked every further action
(`TripApprovalService.ApproveTrip`'s own pre-check reads that same column and returns "already

## Phase 17 - Generalized the Approval Engine: any mode can have N dynamically-typed approvers, not
## just `selected_employee_override` (2026-10-07)

User-driven architectural change, explicitly requested to "skip any and all legacy code": the engine
had two hardcoded approver "types" baked into `HR_ApprovalConfig` itself -
`isFinanceApproverRequired`/`financeApproverId` and `isHrRequired`/`hrApproverId`, each a single fixed
employee, used only by `default_chain` mode. Every other mode already drew its approver pool from the
generic `HR_ApprovalConfigApprover` table (arbitrary count, free-text `ApprovalType`/`Designation`) -
this phase extends that same mechanism to `default_chain`, so **every** mode now supports an arbitrary
number of approvers, each with any free-text type ("Logistics Approver", "Legal Approver", not limited
to "HR"/"Finance").

**Reporting Manager stays untouched and special-cased** (`HR_ApprovalConfig.IsReportingMgrRequired`) -
by design, it is always resolved dynamically from the requester's own `ReportingPersonID`, never a
manually picked employee, so it was never a candidate for this generalization.

**Schema**: `Migration_AddApprovalConfigApproverStageOrder_20261007.sql` adds
`HR_ApprovalConfigApprover.StageOrder` (`INT NOT NULL DEFAULT 0`). Only meaningful for
`default_chain`: rows sharing a `StageOrder` run together as one Unanimous stage; stages advance in
ascending `StageOrder` order, after the Reporting Manager stage (if any). Every other mode ignores it
(always single-stage) - decided via `AskUserQuestion` (explicit order field, not insertion order, so
an admin can reorder without re-adding rows).

**Engine (`ApprovalRepository.BuildStepsAsync`)**: the `default_chain` branch no longer reads
`config.IsHrRequired`/`HrApproverId`/`IsFinanceApproverRequired`/`FinanceApproverId` at all - it now
calls the same `GetConfigApproversAsync` every other mode uses, groups the result by `StageOrder`
(`GroupBy(a => a.StageOrder).OrderBy(g => g.Key)`), and emits one `Unanimous` stage per group, stacked
after the optional RM stage. `ApprovalConfigRow`/`ResolveConfigSql` had the now-unused
Finance/HR columns removed entirely (clean cut at the engine's only read site).

**Decision on the old `HR_ApprovalConfig` columns** (`AskUserQuestion`, user chose "stop using them in
code, leave columns in DB for now"): the physical columns are untouched - they're still read directly
by Travel Management's own **not-yet-engine-migrated** legacy screens
(`ApproveTravelExpenseRepository`, `TravelPaymentRepository`, `TravelSettlementRepository`,
`TravelSetupRepository.BuildApprovalSeedAsync`'s legacy-mirror seeding), which key off their *own*,
separate `HR_ApprovalConfig` rows (different `FormDocNo` than "Trip Request Approval"/"Advance Payment
Approval") and are entirely unaffected by this change - confirmed by checking that
`TravelConfigRepository` is the only place in the codebase that ever writes `HR_ApprovalConfig`, i.e.
the single shared admin config surface for every module.

**Admin config write path (`TravelConfigRepository.SyncTravelConfigApproversAsync`)**: removed the
mode-gate that only ever persisted `HR_ApprovalConfigApprover` rows for
`any_one`/`selected_employee_override`/`first_decision_wins` - `default_chain` now persists its list
the same way. `StageOrder` flows through the INSERT. `TravelConfigService.ValidateTravelConfigPayload`
extended to also employee-id-validate `default_chain`'s `selectedApprovers` (same check already applied
to `any_one`/`first_decision_wins`). The old Finance/HR single-id validation block is left in place
(harmless no-op once those flags are simply never set true by an updated frontend).

**Display (`ListApproveByIdDto`)**: `_BuildApprovals()` now prefers `EngineSteps` (the authoritative
`HR_ApprovalStep` data, added in Phase 15b) for **every** mode once an instance exists, not just
`selected_employee_override` - `default_chain`'s old fixed "3 role" display (`BuildThreeRoleSteps`,
reading `ReportingManagerEmpId`/`FinanceApproverEmpId`/`HrManagerEmpId`) would otherwise have shown
nothing for a config's new dynamic (non-RM/HR/Finance-keyword) approvers, since Travel's legacy mirror
only ever maps the first 3 generic approvers into those 3 columns (Phase 14's known gap). The
old per-mode boolean-based builders remain only as the fallback for rows with no engine instance at
all (pre-migration).

**Explicitly out of scope this pass** (flagged, not done): the Angular `admin/hr-config/form` screen
itself - this phase is backend-only; see the FE contract doc (`Approval-Engine-API-Contract.md` §7.2)
for the exact `selectedApprovers`/`stageOrder` shape the frontend needs to build against, including
retiring the dedicated Finance-approver/HR-approver pickers for `default_chain` in favor of a writable/
freesolo approver-type input alongside the employee picker.

Verified: full build (0 errors) + full test suite (402/402) after.

## Phase 18 - Advance Payment Approval given the same GetPending-based authorization Trip Approval got (2026-10-07)

Reported by the user after live-testing `AdvancePaymentApprovalController`: "it seems that everyone can
view/approve things here." Root cause: the Phase 15/16 GetPending-based fix was applied to
`TripApprovalService` only - `AdvancePaymentApprovalService` never got it, and structurally couldn't

`TripApprovalScopeResolver` (list) and `TravelApprovalAccessResolver` (detail/action) checks, both of

never "is the engine's current stage actually waiting on you right now."

**`ListAllAsync`**: rewritten to match `TripApprovalService.ListAllTripApprovals` exactly - resolves

## Phase 19 - Travel Expense Approval wired onto the Approval Engine / HR Config (2026-10-08,
user-requested follow-up: "we need this in our global hr-config approvers")

Scoped per the user's own finding while live-testing: `ApproveTravelExpenseRepository` had no config
slot of its own at all - its `HR_ApprovalConfig` lookup (`ExpenseTravelConfigJoinSql`,
`BuildApprovalStepsAsync`) was keyed off `a.FormDocId`, where `a` is the trip's own
`HR_TM_TripRequestApproval` row, which is *always* the **Trip Request Approval** FormDoc (confirmed:
no "Travel Expense Approval" FormDoc existed anywhere in the codebase). So this screen was silently
reusing Trip Request Approval's config row - an admin configuring a dedicated expense-approval entry
in HR Config would never have been read by this screen at all. This was Phase 8's own explicit
carve-out ("Explicitly out of scope: Travel Expense approval... needs real design work, not a
mechanical swap") finally being done.

**Scope for this pass** (matching how Phase 8 itself was split - wiring now, visibility rewrite later):
1. A dedicated FormDoc + engine wiring so the screen has its own HR Config slot and the engine becomes
   the real authorization boundary for the Approve/Reject action.
2. **Explicitly deferred, not done this pass**: rewriting `GetSubmittedEmployees`/
   `GetSubmittedExpenseGrid` onto strict `GetPending`-based visibility (Phase 15/16/18's "single most
   relearned lesson"). Today's `ApproverViewerWhereSql` (legacy trip-row columns + a hand-rolled
   `HR_ApprovalConfigApprover` `EXISTS`) stays as the list filter for now - it's a *display* filter,
   not an authorization boundary, and switching it to `GetPending` now would hide every currently
   in-flight expense submission (none has an engine instance yet) until resubmitted. Flagged as the
   natural next follow-up, not silently done - same reasoning Phase 8 used to defer it the first time.

**New FormDoc**: `TravelFormNames.ExpenseApproval = "Travel Expense Approval"`
(`SolutionOne_Core/TravelManagementModels/TravelSetup/TravelFormNames.cs`), self-seeded via
`TravelSetupRepository.EnsureTravelFormDocsAsync` alongside the other two Travel FormDocs (Travel
Management's own established runtime-seeding convention - no SQL migration file needed, unlike every
other module's `Migration_*ApprovalFormDoc_*.sql`). Seeded on the next trip-create/validate call, so it
exists in HR Config (`admin/hr-config/form`) well before any expense is ever submitted against it.

**Submission side** (`TripExpenseSubmitRepository.FinalSubmitTripExpenseToAuthorityAsync`):
`TransactionRecordId` is `TripExpenseSubmitId` - not `TripRequestApprovalId` and not `TripRequestId` -
since this is its own independent approval track, finalized once per (TripRequestApprovalId,
EmployeeId) submission, distinct from the Trip Request/Advance Payment instances already keyed off the
trip itself. Captured via `OUTPUT INSERTED.TripExpenseSubmitId` on the existing `UPDATE ... SET
IsSubmit = 1` statement (previously a plain `ExecuteAsync`). `CreateInstance` runs as its own, separate,
already-completed step *after* this method's own commit (company/branch resolved via a small follow-up
query joining `HR_TM_TripRequestApproval` -> `HR_TM_TripRequest`) - non-fatal, logged only, identical
principle to `TripRequestRepository.TryCreateEngineInstanceAsync`.

**Action side** (`ApproveTravelExpenseRepository.SaveExpenseApprovalAsync`): this method previously
opened its own transaction (`_context.BeginTransactionAsync()`) as its *very first* line, before even
loading `meta`/steps - had to be restructured so all of that resolution (plus the existing
isAdmin/`step.ApproverEmployeeId` authorization check) now happens *before* the transaction opens, so
the engine's `ActionAsync` call (which manages its own transaction on the same scoped `IDapperContext`)
never nests inside it. `EmployeeId` passed to `ActionAsync` is `approverEmployeeIdForSave` (the step's
own resolved approver), not the raw caller id - this is what already made the existing `isAdmin`
override work for the legacy mirror write, and matches the engine's own documented convention (Comp-Off/
Attendance Adjustment/FNF) for admin-override identity. `NotAuthorizedApproverException`/
`InstanceAlreadyClosedException` are left to propagate uncaught out of the repository (nothing is
written yet at that point, so there is nothing to roll back) and are now mapped in
`ApproveTravelExpenseService.SaveExpenseApprovalAsync` to 403/409, matching every other migrated
module's service-layer contract.

**`HR_TM_TripExpenseSubmit.SubmitStatus` is now engine-driven once an instance exists**: previously only
ever flipped to `approved`/`submitted` by re-running the bespoke `BuildApprovalStepsAsync` +
`HR_TM_TripExpenseSubmitApprovalLine` computation after every save (and had no way to ever reach
`rejected` at all, despite the `SubmitStatus` CHECK constraint allowing it). Now, when an engine instance
exists, `engineResult.OverallStatus` (Approved/Rejected/Pending) is authoritative and drives
`submitted`/`approved`/`rejected` directly; the legacy recomputation is kept only as the fallback for
pre-migration submissions with no instance. `UpdateTripExpenseSubmitStatusAsync` signature changed from
`bool allStepsApproved` to the resolved `string submitStatus` to carry the new `rejected` case.

**Dual-write, not non-authoritative mirror** - same architecture as Phase 8's Trip Request/Advance
Payment, not Leave's `HR_LeaveAppAuthLeavel` treatment: `HR_TM_TripExpenseSubmitApprovalLine` is not an
independent, battle-tested workflow engine, it's a thin `MERGE`-upserted mirror over the *same*
`HR_ApprovalConfig`/`HR_ApprovalConfigApprover` tables the generic engine itself reads - architecturally
identical in kind to Trip/Advance Payment, so the engine becomes the real authorization boundary and the
legacy table continues to be written purely for the existing display/detail screen.

**Known, accepted limitation (not fixed this pass, matches Phase 17's own carve-out)**: the bespoke
`BuildApprovalStepsAsync`'s `default_chain` branch still only builds 3 fixed named roles (Reporting
Manager/Finance/HR, from `IsReportingMgrRequired`/`isFinanceApproverRequired`/`isHrRequired` + single
`FinanceApproverId`/`HrApproverId` columns) and never calls `GetConfigApproversAsync` for that mode
(unlike `any_one`/`selected_employee_override`, which already do). The engine itself fully supports
arbitrary N approvers with `StageOrder` grouping under `default_chain` (Phase 17) - so if an admin
configures, say, two Finance approvers for "Travel Expense Approval" under `default_chain`, the engine's
`ActionAsync` will correctly require both, but this screen's own step *display* and
`payload.ApprovalType` matching will still only show/accept the single legacy "Finance Approval Manager"
slot. Reconciling the bespoke display with the engine's `GetInstanceTimelineAsync` (same fix already
applied to `ListApproveByIdDto._BuildApprovals` in Phase 17) needs a frontend contract change and is
explicitly out of scope here, matching Phase 17's own "explicitly out of scope this pass" carve-out for
this exact screen.

**Behavior change worth flagging explicitly** (not hidden): today's bespoke `default_chain` steps
(Reporting Manager/Finance/HR) are fully parallel - any can decide in any order, nothing blocks on
another. The engine's `default_chain` always resolves Reporting Manager at `StageOrder` 0 strictly
before any configured-approver stage, so whatever mode gets configured for "Travel Expense Approval" in
HR Config, the Reporting Manager stage will now gate the rest. This brings the Expense screen in line
with how Trip Request Approval and Advance Payment Approval already behave (both migrated under the
same `default_chain` semantics in Phase 8), rather than preserving Expense's own previously-independent
parallel rule.

## Phase 20 - Hardcoded "Approved = 1" literal, found and fixed across 4 files (2026-10-08)

Unrelated to the Approval Engine migration itself, but the same root cause bit four different Travel
Management screens: `GetApprovalStatusIdsAsync` (`TravelSetupRepository`) resolves "Approved" **by
matching the `Status` text** in `HR_ApprovalStatusMaster` (falling back to literal `1` only if no name
match is found) - `HR_ApprovalStatusMaster` was itself renamed from the legacy `HR_TM_StatusMaster`

live DB, "Approved" is actually `Id = 4`, not `1`.** Everywhere that correctly calls
`GetApprovalStatusIdsAsync()` and compares against `@ApprovedStatusId` was unaffected; everywhere that
hardcoded the literal `1` directly in SQL silently matched the wrong status (or nothing) and returned
empty results with no error - the user's first three reports in this conversation were each this exact
bug in a different file.

Found and fixed, in the order reported:
1. `TravelPaymentRepository.GetAdvancePaymentGrid` + the `SaveTravelAdvanceLines` eligibility check -
   "No advance trips found for this branch" despite an approved advance payment existing.
2. `TripExpenseSubmitRepository.GetPageDataAsync` + `TripBelongsToEmployeeAsync` - `GetPageData`
   returning empty `approvedTrips` despite the trip being approved (the latter also silently gated
   `FinalSubmitTripExpenseToAuthorityAsync`/`SaveTripExpenseSubmitAsync`, not just the page load).
3. `TravelSettlementRepository.GetSettlementGridAsync` (4 occurrences, including inside the
   `SettlementAdvanceDisbursementGateSql` shared const) + `SaveSettlementAsync`'s eligibility check -
   "No trips ready for settlement" despite the trip/advance/expense all being approved.
4. `TravelReportRepository`'s lifecycle report (`BuildLifecycleSql`'s `advSum` OUTER APPLY) - found by

All four fixed the same way: inject `ITravelSetupRepository`, resolve
`var statusIds = await _travelSetup.GetApprovalStatusIdsAsync();` once per call, pass

`HR_ApprovalStatusMaster`). Deliberately left untouched: `tr.Status`/`emp.Status`/`a.IsDeleted`-style
columns, which are unrelated bit "active" flags in a completely different value space, not approval
statuses - conflating the two would be a new bug, not a fix.

No remaining `.Status = 1`/`= 2`/`= 3` literals against an approval-status column anywhere left in

## Phase 23: Approve Travel Expense admin bypass ignored the `approverViewerEmpId` override

After Phase 22, an employee with an "admin" role could still see every submission regardless of
`?approverViewerEmpId=<id>`. Root cause wasn't the new engine-based filter (confirmed working) - it was
`ApproveTravelExpenseController.ResolveApproverViewerEmpId` checking `ResolveIsAdmin(user)` **before**
ever looking at the query override:

```csharp
if (ResolveIsAdmin(user)) return null;   // old order - override never reached for an admin role
```

`ResolveIsAdmin` → `TravelRoleScopePolicy.IsTravelAdmin` → `IsCompanyWideRole` treats any role name
containing `"admin"`/`"hr"`/`"system"`/etc. as company-wide, forcing `null` (no filter, see
everything) - with every current test account literally having role "admin" (confirmed by the user:
"admin only. All are admins for now"), the `approverViewerEmpId` query parameter had been a permanent
no-op for the entire session, regardless of what Phase 22 fixed underneath it.

**Fix**: reordered so an explicit `approverViewerEmpId` override always wins, admin or not - this is
what lets an Admin-role account deliberately impersonate a specific employee's view (clearly this
parameter's intended purpose, used throughout this file's manual testing). An admin calling **without**
an override still defaults to seeing everything, unchanged. Non-admin callers are unaffected either way
(their own JWT employee claim already took priority in practice, since `ResolveIsAdmin` was `false` for
them).

This was purely a controller-level identity-resolution bug, not a flaw in Phase 21/22's filtering
logic - once the real intended employee id reaches the service/repository layer, the engine-based
visibility check already in place works correctly.

Verified: full build (0 errors) + full test suite (402/402) after.

existing pattern); `GetById` returns the id only, matching that endpoint's existing

convention: optional, unvalidated against `HR_EmployeeMaster`).

**Travel Management's legacy 3-column mirror** (`TravelSetupRepository.BuildApprovalSeedAsync`): found

no manager would have stored a bogus `ReportingManagerEmpId` of `0` instead of null on this display

**Creation-time gate** (`TravelSetupRepository.ValidateFormAndConfigAsync`, per spec §4): now only

needed - `TravelSetupValidationDto.Warnings` already existed, unused for this case until now).

decisions made while scoping it with the user. Frontend-facing contract:
`Specs/Approval-Admin-Override-And-Group-Selectors-API-Contract.md`.

**Decisions (user-confirmed 2026-10-09)**
1. **One source of truth for roles**: `HR_UserRoles` + `HR_RolesMaster` only. Department/designation
   from `HR_EmployeeMaster` only. Approvers from `HR_ApprovalConfigApprover` only. The legacy
   `HR_UserMaster.Role` string / `UserRole` token claim is no longer read by anything new (the ~10
   existing hand-rolled `IsAdmin` helpers are NOT migrated yet - separate batches, per user).
2. **"Admin" is a role flag, not a role name**: `HR_RolesMaster.IsSuperAdmin`. Holders get every
   menu x action (`PermissionResolver`, user overrides cannot revoke) and `ICurrentUserAccess.IsAdmin`.
   Splitting Admin vs HR Admin later = untick the flag on a role.
3. **Approval admin override** = a per-company DB setting (`HR_SystemSetting`, key
   `Approval.AdminOverride`, default OFF = unchanged behaviour). When ON, an admin sees every pending
   approval of the company (`GetPending`/`GetTeamRequests`) and may decide any of them; one admin
   decision closes the stage. Only admins can flip it.
4. **Group selectors**: multi-select (one config row per selected role/department/designation).
   A stage containing a group selector is `AnyOne`. "Select all" is a frontend convenience - the
   backend stores explicit rows.

**Schema** (idempotent, NOT yet run against any DB): `Migration_AdminOverride_20261009.sql`
(`HR_RolesMaster.IsSuperAdmin` - ADMIN role backfilled to 1, `HR_SystemSetting`,
`HR_ApprovalStep.ActionedByEmployeeId`), `Migration_ApprovalConfigApproverSelector_20261009.sql`
(`SelectorType`/`SelectorId`, `EmployeeId` nullable, unique index rebuilt). `HR_RolesMaster` and
`HR_ApprovalConfigApprover` are this backend's own tables, so ALTERing them respects
[[schema_shared_legacy_tables]].

**Code**: `ICurrentUserAccess`/`CurrentUserAccess` (per-request, always-fresh role read);
`ISystemSettingService` + `SystemSettingController` (`GET/PUT api/SystemSetting/ApprovalAdminOverride`,
admin-only, 1-minute cache); `RbacManagementController` `PUT roles/{id}/super-admin` (lock-out guard:
the last super-admin holder can't be switched off) and `IsSuperAdmin` on role create/list;
`IApproverSelectorResolver` (the one definition of group membership; active employees
`HR_EmployeeMaster.Status = 1`, login = `HR_UserMaster.Status = 1`); `ApprovalRepository`
`ResolveConfigApproversAsync` expands selectors at `CreateInstance` time (excludes requester,
de-duplicates per stage, throws `NoApproversResolvedException` if a stage resolves to nobody rather
than silently dropping it); `ApprovalController.ResolveSelector` (admin-only preview);
`TravelConfigService` validates selector rows.

**Behaviour changes worth knowing**
- RBAC `groups/users` and `groups/assign-roles` now 400 on an unknown `groupType` (used to silently
  mean "department" - for assign-roles that bulk-assigned roles to the wrong people). `role` added to
  `groups/users`.
- A step decided under override carries `ActionedByEmployeeId`; the timeline returns
  `actionedByEmployeeId`/`actionedByName`/`isAdminOverride`.
- (Superseded by Phase 27: Travel Management now supports group selectors and the override too.)

**Known gaps / not done**: `TravelConfigService`/HR-Config save endpoints still have no role check
(pre-existing; not changed). `ApprovalRepository` SQL (override paths, selector expansion SQL, both
migrations) has no automated test - no SQL Server in the test project; only the pure rules and the
service layer are covered. Verified: full build (0 errors) + full test suite (467/467, 65 new).


## Phase 27: Group selectors + admin override extended to Travel Management (2026-10-09)

Travel already created real engine instances (Trip Request, Advance Payment, Expense), so group
expansion worked at `CreateInstance` time; what blocked it was legacy code around the engine. Decisions
(user): Travel *expense* admin behaviour moves under the same switch (`Approval.AdminOverride` +
`IsSuperAdmin`) instead of `TravelRoleScopePolicy.IsTravelAdmin` role names; Settlement/Payment are
visible to everyone configured for finance work (finance-labelled group selectors), not one person.

- **Removed** the Phase 26 save-time block that rejected group selectors for Travel form docs.
- **`IApprovalAdminOverride`** (extracted from `ApprovalService`): the one check; Trip/Advance/Expense
  services call it and pass `adminOverrideCompanyId` to `ApproveTrip`/`ApproveAsync`/
  `SaveExpenseApprovalAsync`/`GetPendingAsync` (those use `_approvalRepository` directly, bypassing
  `ApprovalService`).
- **Engine-approver awareness**: `IApprovalRepository.IsApproverOnInstanceAsync`. Advance's detail
  view and approve pre-check (`TravelApprovalAccessResolver`, previously role-name admin or legacy
  assigned-approver columns) now also accept anyone holding a step on the instance. The resolver
  takes `adminOverride` instead of reading role names.
- **Expense**: `SaveExpenseApprovalAsync` - when an engine instance exists the engine is authoritative
  and the legacy mirror-step checks no longer run (they rejected group-resolved approvers); mirror steps
  only supply the display label. Admin no longer acts "as" the step's assigned approver; the engine
  stamps `ActionedByEmployeeId`. Expense list SQL lets engine step-holders through the legacy membership
  filter. Detail steps gain group steps (`isGroupApprover`, `groupName`, `canCurrentUserAct`).
- **Readiness** (`ValidateFormAndConfigAsync`) counts all approver rows, so group-only configs no
  longer read as "no approver selected".
- **Settlement / Advance Payment** lists: "responsible person" fallback now ignores group rows
  (`EmployeeId IS NOT NULL`), and additionally shows the trip to any viewer in a finance-labelled
  (`ApprovalType` contains "fin") role/department/designation selector of the config
  (`ApproverSelectorSql.ViewerInFinanceGroup`). Saves already upsert per trip, so several finance users
  opening the same trip doesn't create duplicate rows (last write wins; no claim/lock added).

**Not changed (still role-name based, `TravelRoleScopePolicy.IsTravelAdmin`)**: Settlement/Payment
controllers' admin = see-all, trip request list scope, travel reports, `TripApprovalScopeResolver`.
Only approval-related admin behaviour moved under the switch. **Untested against a database** - the new
SQL (expense membership clause, finance-group fragment, group-step query, `IsApproverOnInstanceAsync`)
is reviewed, not executed. Verified: build + 475/475 tests (8 new in `TravelApprovalOverrideTests`).


## Phase 28: Service-layer permission enforcement (pilot: RBAC + HR Config) and removal of the APPROVE action (2026-10-09)

Audit that triggered this: `[Permission]` (controller filter) covered 13 of ~1,000 endpoints (474 mutating),
all on 3 Travel controllers; 17 more were commented out. Everything else was `[Authorize]` only - a role
without CREATE/UPDATE/DELETE was a UI courtesy. Worst case: every RBAC admin endpoint (assign roles to a
user, assign permissions to a role, user overrides, group role assignment) was open to any logged-in user.

**Decisions (user, 2026-10-09)**: delete the `APPROVE` action (the approval engine, not a role permission,
decides who approves); enforce CREATE/UPDATE/DELETE at the **service layer**, not repositories (they are
called by system flows with no user behind them); no audit/log-only phase; pilot RBAC + approval
configuration (HR Config) first, then the rest module by module. All current users are admins, so nothing
locks out during testing.

- **Migration** `Migration_RemoveApproveAction_20261009.sql`: deletes `HR_UserPermissions` ->
  `HR_RolePermissions` -> `HR_MenuActions` rows for APPROVE. Removed `Actions.Approve`; the two
  `[Permission(..., Approve)]` on `ApproveTravelExpenseController`: `SaveExpenseApproval` now has none
  (engine gate), `BackfillApprovalInstances` (bulk admin op) is `Update`.
- **Mechanism**: `[RequiresPermission(module, action)]` on service-INTERFACE methods;
  `PermissionGuardProxy<T>` (DispatchProxy decorator) enforces it via `IPermissionChecker`; register with
  `AddPermissionGuarded<TService, TImpl>()` (the impl itself is not registered, so nothing can bypass it).
  Denied -> 403 `ResponseModel`/`ResponseModel<T>`; other return types throw `PermissionDeniedException`.
  Unmarked methods are open (self-service stays available). Marked non-async methods fail fast at resolve.
- **Checker**: super-admin always passes (even for a module with no menu row); otherwise role grants +
  per-user overrides, case-insensitive, same cache key as `PermissionFilter` (shared eviction). A module is
  its `HR_MenuItems.MainMenu` code OR `NavigateUrl` (`Modules.RoleAdministration = "/admin/rbac"`,
  `Modules.HrConfig = "/admin/hr-config"`).
- **Pilot marks**: `IRbacManagementService` create/delete/assign/set/remove methods; `ITravelConfigService`
  insert/update/delete/create-form-doc/update-menu-link. Reads are open (lookup lists feed other screens).
  `EveryWriteMethodOnAPilotService_IsMarkedRequiresPermission` fails if a new write method is added unmarked.
- **Internal callers**: `PermissionGuardBypass.Begin()` (AsyncLocal scope) used by `UserService` and
  `CandidateTransitionService` when they assign roles during user creation / candidate transition.
- **Escalation rule** (applies even inside a bypass): only an admin may assign a super-admin role
  (`AssignRolesToUser`, `AssignRolesToGroup`) - holding RBAC UPDATE is not a way to mint admins.
- **Bug fixed on the way**: `PermissionRepository.GetUserPermissionOverridesAsync` selected only
  UserId/MenuID/ActionID, so `MenuCode`/`ActionCode`/`IsRevoked` were never populated and every per-user
  override resolved to a junk `":"` entry - overrides had no effect. It now returns the codes and honours
  `IsGranted`/`IsRevoked` and the effective window. Behaviour change: existing overrides start working.
  Also: `SetRoleSuperAdminAsync` now evicts holders' cached permission sets.

**Not done yet**: every other module (rollout plan: one module at a time, annotate the service interface,
switch its DI line to `AddPermissionGuarded`, add its menu/route constant). `PermissionFilter` on
controllers is unchanged. Untested against a DB: the migration, `AnySuperAdminRoleAsync`, the override query.
Verified: build + 504 tests (29 new).


## Phase 29: Service-layer permission enforcement rolled out to Travel Management (2026-10-09)

Same mechanism as Phase 28. No Travel service has an internal service-to-service caller, so no
`PermissionGuardBypass` was needed. DI: nine Travel services moved to `AddPermissionGuarded`
(`ITripExpenseSubmitService` was registered twice; now once).

| Service | Marked methods (module -> action) |
|---|---|
| `ITripRequestService` | `InsertTripRequest`, `InsertTripRequestRange` -> Create; `UpdateTripRequestRange` -> Update; `DeleteTripRequest` -> Delete (`/travel-management/trip-request`) |
| `ITripApprovalService` | `UpdateTripApproval` -> Update; `DeleteTripApproval` -> Delete (`/travel-management/trip-approval`) |
| `ITravelPolicyService` | Insert / Update / Delete (`/travel-management/travel-policy`) |
| `ITravelPaymentService` | `DeleteTravelPayment` -> Delete (`Advance Payment`) |
| `ITravelSettlementService` | `SaveSettlementAsync` -> Update (`Expense Settlement`) |
| `ITripExpenseSubmitService` | `SubmitTripExpenseAsync` -> Create; `SaveTripExpenseDisplayStatusAsync`, `FinalSubmitTripExpenseToAuthorityAsync` -> Update (`/travel-management/trip-expense-submit`) |
| `IApproveTravelExpenseService` | `BackfillApprovalInstancesAsync` -> Update (`Approve Expense`) |
| `ITravelConfigService` | already guarded in Phase 28 (`/admin/hr-config`) |

**Deliberately unmarked**: `ApproveTrip`, `ApproveAsync` (advance), `SaveExpenseApprovalAsync` - approval
decisions belong to the Approval Engine; `SaveTravelPayment` - one method behind both the Create ("insert")
and Update ("update") endpoints, which keep their controller-level `[Permission]`. A test lists these and
fails if any other write-looking Travel method is added unmarked, and checks approvals are never marked.
The module constants for the three screens that already had a controller `[Permission]` keep their
MainMenu-code form so the service mark and the controller attribute always agree; the others use routes.

**Not guarded**: reads, `ITripExpenseDocumentUploadService` (generic `ICommonDocumentUploadService<,,>`
shared by other modules - uploading/deleting expense documents needs a module-aware approach, left for the
document-upload pass), `TravelDashboard`/`TravelReport` (reads). **Self-service note**: employees creating
trip requests / submitting expenses now need CREATE/UPDATE on those menus via their role - the "Employee"
role(s) must be granted them before non-admin users go live. Verified: build + 524 tests (20 new).

## Phase 31: RBAC Menu Groups (2026-10-10)

Implements `hrmsystemfe/docs/specs/RBAC-Menu-Groups-Backend-Spec.md`: two tables, four endpoints, no side
effects. `Migration_RbacScreenGroups_20261010.sql`; own `IMenuGroupRepository`/`IMenuGroupService`/
`MenuGroupController` (the RBAC repository was already past the 500-line guideline), same
`api/RbacManagement/menu-groups` URLs. Writes are `[RequiresPermission]` on `/admin/rbac` (Create/Update/
Delete) via `AddPermissionGuarded`, the list is open.

**Spec corrections resolved**: `HR_MenuItems` key is `MenuID` BIGINT, so `HR_MenuGroupItems.MenuId` is BIGINT
(the sketch said INT); roles are global (no company column) so groups are global - no `CompanyId`, unique on
`GroupName`; FK to `HR_MenuItems` is `ON DELETE CASCADE` so menu cleanup is never blocked by a label; the
frontend's `ApiService.delete()` sends **POST**, so `.../{id}/delete` is `[HttpPost]` (`[HttpDelete]` also
accepted). Update/delete of an unknown group = 404; name uniqueness is case-insensitive with a race-safe
unique-constraint fallback to 400. Verified: build + 546 tests (19 new). SQL untested against a DB.

**Phase 31 follow-up (2026-10-10)**: running the first version on the dev DB failed (Msg 1778) because
`HR_MenuGroups` already existed with a non-INT `GroupID`, so the INT `GroupId` FK on the items table could not
match; the script also tried to index the items table that had failed to create. Fixed: the migration now
adapts to existing tables (creates `HR_MenuGroupItems.GroupId` with the SAME type as `HR_MenuGroups`' primary
key, read from the catalog; adds missing audit columns; rebuilds an existing items table whose id types
differ; only indexes when the table exists), and the group id is `long` end to end (DTO, repository, service,
`{groupId:long}` routes) so either BIGINT or INT in the database works. New tables created by the script now
use BIGINT ids.

**Phase 31 correction (2026-10-10) - table names**: `HR_MenuGroups` is NOT free to use: it is the
left-navigation folder tree (`vw_HR_MenuGroupTree`), shared with the sibling `hr_payroll` project - a
legacy-shared table ([[schema_shared_legacy_tables]]). The earlier drafts of this feature were written
against that name (the last one even "adapted" to it by adding columns/an index when it existed). The
feature now owns two brand-new tables, `HR_RbacScreenGroups` / `HR_RbacScreenGroupItems`
(`Migration_RbacScreenGroups_20261010.sql`, plain create-if-missing, touches nothing else); the API and UI
keep the spec's "menu groups" naming. `Check_MenuGroupsFirstAttempt_20261010.sql` is a READ-ONLY script to
see whether the earlier drafts left anything behind on a database they were run against (columns
`CreatedBy`/`ModifiedBy`/`ModifiedDate` or index `UX_HR_MenuGroups_GroupName` on `HR_MenuGroups`, or a
`HR_MenuGroupItems` table); its DROPs are commented out for you to apply deliberately.

**Phase 31 follow-up (2026-10-10, 405 on menu-group update)**: the frontend's `ApiService.put()` (and
`delete()`) send POST, so the PUT-only routes returned 405 - visible in the log as a preflight with
`Access-Control-Request-Method: POST` on `/menu-groups/1`. The three PUT routes added this session (menu-group
update, `roles/{id}/super-admin`, `SystemSetting/ApprovalAdminOverride`) now also accept POST; a reflection test
fails if a PUT route is added without a matching POST. The super-admin toggle and override switch had the same
latent 405 and are fixed too. Verified: build + 550 tests.
