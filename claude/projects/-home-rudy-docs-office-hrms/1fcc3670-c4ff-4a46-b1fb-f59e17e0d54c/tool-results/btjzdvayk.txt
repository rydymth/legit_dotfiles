  3. **Status modeling**: reuse the existing status master table (renamed generically, see Phase 2) rather than the spec's varchar+CHECK columns - keeps one status vocabulary instead of two, and Travel Management's `StatusName`-driven UI needs no translation layer once it eventually migrates. **Bug caught and fixed while wiring Recruitment**: `ResolveConfigSql`'s branch-match condition (`ac.BranchMasterId = @branchMasterId`) is never TRUE when both sides are NULL (SQL's three-valued logic) - and `HR_RecruitmentRequisition` has no `BranchMasterId` column at all, so Recruitment always calls `CreateInstance` with a null branch. Without the fix, a deliberately branch-agnostic (NULL) config row would silently fail its exact-match test and fall through to the global fallback arm - wrong result for exactly the module this table exists for. Fixed with `ISNULL(x, -1) = ISNULL(y, -1)` pairing on both sides.

**Cut over (2026-09-28, user decision)**: `UpdateApprovalRecruitmentRequisition`, `UpdateHRStatusRequisition`, `GetAllRecruitmentRequisitions` now route through the engine; `GetHRApprovalRequisitionList` deliberately does not (see below).

- **Design gap found while wiring this**: Recruitment has *two* independent approval tracks over the same `HR_RecruitmentRequisition` row ("Raise Requisition", "HR Approve Requisition" - spec §3.1), but the additive `ApprovalInstanceId` column (spec §3.6) only has room for one FK. Fixed by adding `IApprovalRepository.GetInstanceIdAsync(formDocId, transactionRecordId)`, which resolves either track independently via `HR_ApprovalInstance`'s own `UQ_HR_ApprovalInstance_Transaction` key. `ApprovalInstanceId` is kept only as a "most recently touched instance" convenience pointer, not the source of truth.
- **Cross-FormDoc chaining decision**: nothing in the spec says when the "HR Approve Requisition" instance gets created. Went with: when the raise-approval `Action` call closes `Approved`, `UpdateApprovalRecruitmentRequisition` immediately calls `CreateInstance` for "HR Approve Requisition" over the same row. This matches this codebase's own pre-existing intent - `GetHRApprovalRequisitionList`'s doc comment already said `[Status = Approved]` before any of this work started. Not spec-confirmed, flagged here in case wrong.
- **`GetHRApprovalRequisitionList` filtering (2026-09-28, user confirmed)**: initially left unfiltered on purpose, since its doc comment documented a prior deliberate "show all" decision. User explicitly asked to apply the same `GetPending`-based filtering here too, so this now shows only what's Pending on the caller at the "HR Approve Requisition" stage (FormDocId 2) - same mechanism as `GetAllRecruitmentRequisitions(applyApproverFilter: true)`, just against the other FormDoc.
- **"Reopen" transitions bypass the engine entirely**: `ApprovalStatus`/`HRStatus` values other than "Approved"/"Rejected" (case-insensitive) skip `Action` and fall through to the old column-update path unchanged - the engine's Pending→terminal state machine has no concept of reopening a closed instance, and inventing one wasn't asked for.
- **New real enforcement, not just a data-source swap**: both actions previously had zero server-side authorization - any authenticated caller could set any status on any requisition Id. `Action`'s pending-step lookup is now the actual boundary.

## Phase 8 - Travel Management migration (2026-09-28, user-requested follow-up)

Scoped via a research pass before any code: "migrate Travel Management" turned out to be three
differently-sized jobs, not one. Decisions:
1. **In scope this pass**: Trip Request approval + Advance Payment approval (share `HR_TM_TripRequestApproval`, differentiated by `FormDocId`/`FormName` - straightforward, same shape as Recruitment).
2. **Explicitly out of scope**: Travel Expense approval. It does NOT use `HR_TM_TripRequestApproval` at all - its steps are rebuilt dynamically on every read (`ApproveTravelExpenseRepository.BuildApprovalStepsAsync`) from live config, with its own duplicated any-one/unanimous logic and its own auth check, backed by `HR_TM_TripExpenseSubmit.SubmitStatus` + `HR_TM_TripExpenseSubmitApprovalLine` (a separate, `MERGE`-upserted table with defensive "does this exist yet" fallback code suggesting it's newer/less settled). Migrating this needs real design work (how dynamically-rebuilt steps map onto persisted `HR_ApprovalStep` rows), not a mechanical swap - a separate future module.
3. **Company/Branch-wide role visibility** (`TravelRoleScopeOptions`/`TripApprovalScopeResolver` - Travel Admins see the whole company, Finance/Accounts see their whole branch, regardless of personal approver assignment): the new engine's `GetPending` has no equivalent (it only ever answers "do I personally have a pending step"). **Not built as new engine capability this pass** - solved implicitly instead, see the dual-write decision below. Long-term direction (user-stated): don't revive the old appsettings-role-list mechanism as a bolt-on - the real fix is generalizing `HR_ApprovalConfig`/`HR_ApprovalConfigApprover` to accept *roles* as approvers/viewers directly, not just individual employees, once employee-level migration is solid. That's a real future piece of work, not started.

### Follow-up fix (2026-10-05): the approval queue itself had no caller-scoping at all

Once the user configured `HR_ApprovalConfig` for "Income Tax Proof Approval" for real and started
testing, it turned out `IncomeTaxProofApprovalService.GetQueueAsync` (the approval screen's list
endpoint) had **zero server-side visibility scoping** - not even company-level, let alone
per-approver. `IncomeTaxProofApprovalRepository.GetQueueAsync`'s only filters were the two
*optional*, caller-supplied `BranchMasterID`/`CategoryMasterID` query params; omit both (nothing
forced a caller to send them) and any authenticated user saw every pending submission across every
company. The `SaveAsync` gate (above) was always correct, but it only blocks the *decide* action -
the list itself was wide open regardless of whether the config existed.

Two fixes, both following established precedent rather than inventing new patterns:
- **Company scoping, unconditional**: `IIncomeTaxProofApprovalRepository.GetQueueAsync` now takes
  `companyMasterId` and the SQL adds `AND e.CompanyMasterID = @CompanyMasterId` - the one filter
  that was never optional and should never have been caller-omittable.
- **Approver-only visibility, same mechanism as Recruitment's `applyApproverFilter`**:
  `IncomeTaxProofApprovalService.GetQueueAsync` now resolves the caller's actually-Pending
  submissions via `IApprovalService.GetPending(formDocId, employeeId)` and filters the queue down to
  those `TransactionRecordId`s - identical to
  `RecruitmentRequisitionService.GetAllRecruitmentRequisitions(applyApproverFilter: true)`/
  `GetHRApprovalRequisitionList`.
- [x] Full build + full test suite (402/402) passing

**Correction, same day**: the first pass of this fix exempted HR Admin from the filter (full
company-wide view), borrowed from `IncomeTaxProofSubmissionService.GetAllAsync`'s own convention for
the sibling submission screen. **Wrong precedent to copy** - the user's test account is Admin-role
only (no separate non-admin test identity exists in this environment), and Recruitment's own
`applyApproverFilter` has **no role-based exemption at all**: an Admin there only sees what their
own employee record is actually the configured approver for, same as anyone else. Removed the
exemption entirely so Income Tax now matches Recruitment's behavior exactly, with zero bypass for
any role. If a genuine company-wide oversight view is wanted later, it should be its own explicit,
caller-requested toggle (mirroring Recruitment's own `applyApproverFilter` parameter), not a silent
role check baked into the one list endpoint.

## Phase 11 - Broader module rollout, module 7: FNF (2026-09-30)

**FNF (Full & Final Settlement) Approval** - done. Scoped via a dedicated research pass first (per
the user's own explicit request to understand the problems before implementing), which corrected
the original "separate, later conversation" framing in both directions:

- **Overcautious on transaction risk**: `FnfSettlementRepository` shares the exact same scoped
  `IDapperContext` as `ApprovalRepository`, but every one of its methods opens and commits its OWN
  independent transaction - there is no single transaction wrapping Approve's cascading side
  effects (push to payroll, settle loan schedule). This is actually the simplest transaction shape
  of the whole rollout - placing the engine gate as its own step before `ApproveCaseHeaderAsync`
  is safe, same discipline as every prior module.
- **Undercounted on authorization**: there was no "no approver-config concept", there was **no
  decision-level authorization at all** - `FnfCaseService.ApproveAsync`/`RejectAsync` checked only
  `WorkflowStatus`/checklist completeness, nothing case-specific, not even a blanket `IsAdmin()`
  check like Loan/Assets/Comp-Off had before their own migrations. This migration is genuinely
  adding real enforcement where none existed, not translating an existing rule.
- **Side effects entangle two other modules, neither in conflict**: Approve pushes into
  `HR_EmployeeWiseSalaryHead`/`HR_SalaryAdditionalHead` (plain payroll config tables, never
  approval-gated) and marks `HR_LoanEMISchedule.IsPaid` (an accounting/schedule table, distinct
  from `HR_LoanRequests`/`HR_LoanApproval` which Loan Request Approval already gates) - no
  interaction with any already-migrated gate.
- Single case, single decision, no batching - simplest shape of the whole rollout.

**A real, FNF-specific design problem found while wiring this, not present in any prior module**:
`RejectAsync` returns a rejected case to Draft for the SAME `caseId`, and the preparer is expected to
edit and resubmit it - a normal, common, expected part of this workflow (unlike every other
module's reject-is-terminal shape). Since `HR_ApprovalInstance` is uniquely keyed on
`(FormDocId, TransactionRecordId)` with no "reopen" concept (same gap already accepted for
Recruitment's Reopen transitions), a resubmission's `CreateInstance` call always fails on the
duplicate key (caught, logged, non-fatal) - and a subsequent decision would then resolve to the
STALE, already-closed instance from the first cycle. Handled by having the gate treat "instance
already closed" (HTTP 409, from `InstanceAlreadyClosedException`) as "fall through to the legacy
`WorkflowStatus` check" rather than a hard refusal, while still hard-blocking on "not authorized"
(HTTP 403) - the legacy `WorkflowStatus` check plus `ApproveCaseHeaderAsync`/`RejectCaseAsync`'s own
`rows == 0` optimistic-concurrency guard already catch a genuine double-decision race on the same
live pending case, so this doesn't reopen a real hole. **Known, disclosed limitation**: a case that
gets rejected even once permanently loses the new engine-level enforcement on all its future
decisions (every resubmission collides with the same stale instance) - strictly better than the
pre-migration baseline (zero enforcement for every case) but not as strong as first-time-clean
cases get. A real "reopen" capability in the engine would close this gap; not built now, same
"flagged, not solved" precedent as every other cross-cutting engine gap found this rollout.

## Phase 17 - Generalized the Approval Engine: any mode can have N dynamically-typed approvers, not
## just `selected_employee_override` (2026-10-07)

User-driven architectural change, explicitly requested to "skip any and all legacy code": the engine
had two hardcoded approver "types" baked into `HR_ApprovalConfig` itself -
`isFinanceApproverRequired`/`financeApproverId` and `isHrRequired`/`hrApproverId`, each a single fixed
employee, used only by `default_chain` mode. Every other mode already drew its approver pool from the
generic `HR_ApprovalConfigApprover` table (arbitrary count, free-text `ApprovalType`/`Designation`) -
this phase extends that same mechanism to `default_chain`, so **every** mode now supports an arbitrary
number of approvers, each with any free-text type ("Logistics Approver", "Legal Approver", not limited
to "HR"/"Finance").

**Reporting Manager stays untouched and special-cased** (`HR_ApprovalConfig.IsReportingMgrRequired`) -
by design, it is always resolved dynamically from the requester's own `ReportingPersonID`, never a
manually picked employee, so it was never a candidate for this generalization.

**Schema**: `Migration_AddApprovalConfigApproverStageOrder_20261007.sql` adds
`HR_ApprovalConfigApprover.StageOrder` (`INT NOT NULL DEFAULT 0`). Only meaningful for
`default_chain`: rows sharing a `StageOrder` run together as one Unanimous stage; stages advance in
ascending `StageOrder` order, after the Reporting Manager stage (if any). Every other mode ignores it
(always single-stage) - decided via `AskUserQuestion` (explicit order field, not insertion order, so
an admin can reorder without re-adding rows).

**Engine (`ApprovalRepository.BuildStepsAsync`)**: the `default_chain` branch no longer reads
`config.IsHrRequired`/`HrApproverId`/`IsFinanceApproverRequired`/`FinanceApproverId` at all - it now
calls the same `GetConfigApproversAsync` every other mode uses, groups the result by `StageOrder`
(`GroupBy(a => a.StageOrder).OrderBy(g => g.Key)`), and emits one `Unanimous` stage per group, stacked
after the optional RM stage. `ApprovalConfigRow`/`ResolveConfigSql` had the now-unused
Finance/HR columns removed entirely (clean cut at the engine's only read site).

**Decision on the old `HR_ApprovalConfig` columns** (`AskUserQuestion`, user chose "stop using them in
code, leave columns in DB for now"): the physical columns are untouched - they're still read directly
by Travel Management's own **not-yet-engine-migrated** legacy screens
(`ApproveTravelExpenseRepository`, `TravelPaymentRepository`, `TravelSettlementRepository`,
`TravelSetupRepository.BuildApprovalSeedAsync`'s legacy-mirror seeding), which key off their *own*,
separate `HR_ApprovalConfig` rows (different `FormDocNo` than "Trip Request Approval"/"Advance Payment
Approval") and are entirely unaffected by this change - confirmed by checking that
`TravelConfigRepository` is the only place in the codebase that ever writes `HR_ApprovalConfig`, i.e.
the single shared admin config surface for every module.

**Admin config write path (`TravelConfigRepository.SyncTravelConfigApproversAsync`)**: removed the
mode-gate that only ever persisted `HR_ApprovalConfigApprover` rows for
`any_one`/`selected_employee_override`/`first_decision_wins` - `default_chain` now persists its list
the same way. `StageOrder` flows through the INSERT. `TravelConfigService.ValidateTravelConfigPayload`
extended to also employee-id-validate `default_chain`'s `selectedApprovers` (same check already applied
to `any_one`/`first_decision_wins`). The old Finance/HR single-id validation block is left in place
(harmless no-op once those flags are simply never set true by an updated frontend).

**Display (`ListApproveByIdDto`)**: `_BuildApprovals()` now prefers `EngineSteps` (the authoritative
`HR_ApprovalStep` data, added in Phase 15b) for **every** mode once an instance exists, not just
`selected_employee_override` - `default_chain`'s old fixed "3 role" display (`BuildThreeRoleSteps`,
reading `ReportingManagerEmpId`/`FinanceApproverEmpId`/`HrManagerEmpId`) would otherwise have shown
nothing for a config's new dynamic (non-RM/HR/Finance-keyword) approvers, since Travel's legacy mirror
only ever maps the first 3 generic approvers into those 3 columns (Phase 14's known gap). The
old per-mode boolean-based builders remain only as the fallback for rows with no engine instance at
all (pre-migration).

**Explicitly out of scope this pass** (flagged, not done): the Angular `admin/hr-config/form` screen
itself - this phase is backend-only; see the FE contract doc (`Approval-Engine-API-Contract.md` §7.2)
for the exact `selectedApprovers`/`stageOrder` shape the frontend needs to build against, including
retiring the dedicated Finance-approver/HR-approver pickers for `default_chain` in favor of a writable/
freesolo approver-type input alongside the employee picker.
